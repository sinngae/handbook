# 一句话总览
GMP 不是让你日常写业务代码时手动去调度G/M/P；**理解GMP是帮你看懂Go程序的性能瓶颈、阻塞场景、并发陷阱，写出更高效、不踩坑的并发代码**。
很多Go并发问题，根源都来自GMP调度模型，不懂GMP就只能靠猜性能。

下面分场景讲，结合实际编码中会遇到的问题：

## 1. 理解：什么操作会阻塞P，什么不会（最实用）
GMP里最重要的区分：**是否会剥离P**
1. **阻塞系统调用（文件IO、网络syscall）**
G执行syscall阻塞 → M跟着阻塞，但**P会被剥离，交给其他M继续跑G**。
👉 写网络服务时：大量goroutine阻塞在网络IO是安全的，不会卡住整个程序，这是Go高并发的基础。
> 编码启示：大量IO型并发，放心开goroutine。

2. **用户态阻塞（mutex、channel阻塞、time.Sleep）**
G会被标记为Gwaiting，**M不会阻塞，P不会解绑**，M会去P的runq执行其他G。
👉 这类阻塞是runtime在用户态完成调度，代价很低。

3. **纯CPU密集计算（长时间占用G不主动让出）**
会触发**抢占**（Go1.14之后异步抢占）。
> 旧版本Go没有异步抢占，长时间死循环会霸占P，其他G得不到调度；现在虽然有抢占，但CPU密集任务依然会占用P资源。
👉 编码启示：大量CPU计算，会挤占同一个P上其他协程的执行时间；如果GOMAXPROCS=4，最多4个CPU密集G并行跑。

> ❗重点坑：**runtime.Gosched()**
很多人以为Gosched一定会让出CPU。理解GMP就知道：它只是把当前G放回runq，重新调度，不是强制释放P。

## 2. 排查为什么CPU打满、并发上不去
### 场景A：GOMAXPROCS设置不合理
如果你机器8核，但是代码里写了 `runtime.GOMAXPROCS(2)` → 只有2个P，最多同时2个G并行执行。
哪怕开1000个goroutine，CPU最多跑满2核。
> 不懂GMP：疑惑“为什么goroutine这么多，CPU跑不满？”
> 懂GMP：第一反应看GOMAXPROCS。

### 场景B：大量M被创建（M暴涨）
当大量G进入阻塞syscall，P不断剥离，runtime不断新建M。
M是OS内核线程，M太多会造成：OS内核线程切换开销飙升，CPU sys占高。
> 现象：程序变慢，profile看到大量线程。
> 懂GMP：知道是大量阻塞syscall导致M膨胀，需要优化IO并发控制（限流、连接池）。

## 3. 理解锁、channel的性能表现，避免错误优化
1. **sync.Mutex**
- 正常无竞争：用户态自旋，不交出P；
- 锁竞争激烈：G会休眠，P继续跑其他G。
> 理解GMP：不会误以为mutex阻塞会卡住整个P。

2. **不要盲目开无限goroutine**
虽然G很轻（栈初始2KB），但G再多，并行上限依然是GOMAXPROCS个P。
无限创建goroutine：
- IO场景：M会疯狂增长，OS线程压力大；
- CPU场景：再多G也只能最多GOMAXPROCS个并行，剩下排队，还增加调度开销。
> 编码启示：IO并发需要做限流（errgroup、worker池），而不是go func(){}()无限开。

## 4. 看懂pprof、trace工具，定位问题
Go的trace会展示G/P/M状态：Grunning、Gwaiting、Pidle等。
- 如果看到大量Pidle：CPU资源没利用上；
- 如果大量G在syscall阻塞：大量IO阻塞，M数量变多；
- 如果G持续处于running，P被长时间占用：CPU密集任务。

不懂GMP，trace里的G/P/M状态完全看不懂；懂GMP才能定位到底是锁、IO还是CPU导致的性能问题。

## 5. 区分两种抢占，避免踩老版本Go的坑
Go1.14之前只有**协作式抢占**：G必须在函数调用点才会被调度。
如果写一个无函数调用的死循环，会永久霸占P，其他G永远得不到执行。
```go
for {
    // 没有函数调用，Go1.14前无法抢占，卡死P
}
```
Go1.14引入**异步抢占**，通过信号打断G，解决这个问题。
> 编码启示：了解这个机制，就知道CPU密集循环的风险，写长循环时的注意事项。

## 6. 理解GC的行为（GC和P强相关）
GC工作阶段（STW、标记）会和P打交道：
- STW阶段会暂停所有P上运行的G；
- 并行标记阶段会使用多个P一起标记，并行度受GOMAXPROCS影响。
懂GMP就更容易理解GC延迟的来源：长时间运行的G会延长STW等待时间。

# ✅ 哪些东西**不需要你写代码时手动操作**
- 不能手动创建P/M；
- 不能手动绑定G到P；
- 不能控制P交给哪个M；
这些全部由runtime自动管理。GMP属于**底层运行原理，不是API**。

# 📌 一句话总结：编码层面收益
> GMP不会教你怎么写 `go func()`，但会告诉你：
> 什么时候goroutine阻塞会影响整体性能、什么时候不会；
> 为什么CPU跑不满或者sys开销很高；
> 为什么开一万个goroutine不一定变快；
> 怎么看懂trace/pprof定位并发瓶颈。

# 举个真实面试/工作对比
不懂GMP：
> “Go协程很轻，随便开，越多协程并发越高。”

懂GMP：
> “Go协程轻，但并行上限由GOMAXPROCS(P数量)决定；大量IO阻塞会创建大量M，带来内核线程开销；CPU密集场景再多G也无法突破P的并行上限。”
