# 核心一句话
**TCP四次挥手的协议逻辑，是操作系统内核（TCP协议栈）负责执行；应用程序只是发起关闭的“触发方”，不负责跑TCP报文收发。**

## 1. 正常流程：程序调用close()，内核做挥手
1. 应用程序调用 `close(fd)` / `shutdown()`（go/net.Close()、socket.close底层都是这个系统调用）
2. **应用态代码到此任务结束**，后续的FIN、ACK报文全部由操作系统内核TCP栈处理：
    - 内核发出 `FIN`（我这边不再发数据），进入FIN_WAIT_1
    - 对端内核收到FIN，回复ACK（CLOSE_WAIT）
    - 对端应用如果也close，内核发FIN过来
    - 本机内核回复ACK → 完成四次挥手

> 应用**不收发TCP报文**，只是告诉内核：我要关闭这个socket了。TCP状态机、报文、重传、超时全在内核。

## 2. 重点问题：程序异常退出（crash、kill -9、段错误），会正常close吗？
✅ **会！OS会自动帮应用执行socket的close逻辑**
原理：
进程退出时，操作系统内核会**回收该进程所有打开的文件描述符（socket也是fd）**。
内核自动对这些未关闭socket执行close()，**内核会发送FIN包，启动TCP四次挥手**。

### 区分两种kill
1. `kill`（默认SIGTERM，15）：程序有机会捕获信号、做清理；就算程序不处理，进程退出后内核依然回收fd、发FIN。
2. `kill -9`（SIGKILL，强制杀死，**不能被捕获**）：**进程直接被干掉，没有任何用户态清理代码执行，但是！内核依旧会回收fd，发送FIN**。

> 所以哪怕程序直接崩溃、panic、段错误，**只要操作系统还活着**，内核会自动发出FIN，正常走TCP断开流程。

## 3. 但是！有一个经典坑：RST而不是FIN
什么情况**不发FIN，直接发RST（重置连接，粗暴断开，不走四次挥手）**：
> 当socket上**还有未读完的接收缓冲区数据**，进程退出/close，内核会发送RST包，直接断掉连接，跳过优雅四次挥手！

场景举例：
1. 服务端socket收到客户端大量数据，**内核recv缓冲区还有数据没被应用read**
2. 此时服务端进程crash
3. OS关闭fd，发现接收缓冲区还有残留数据 → 直接发送RST给对方
4. 对端收到RST，连接立刻重置，**不是优雅FIN挥手**

> 总结这个关键点：
> - 缓冲区**没有残留待读数据**：进程崩溃 → 内核发FIN，正常四次挥手
> - 缓冲区**还有未读数据**：进程崩溃 → 内核发RST，粗暴断开

## 4. 另外一个边界：机器直接断电 / 内核崩溃
**不是程序crash，是整个服务器宕机**：
操作系统直接停了，TCP内核状态全部丢失，**不会发出FIN/RST任何报文**。
对端会保持连接一段时间（保活tcp_keepalive），直到保活探测超时，判定连接死亡。

## 5. 容易混淆两个概念
1. **优雅关闭（FIN，四次挥手）**：双方完成数据收尾，正常断开
2. **强制重置（RST）**：丢弃缓冲区，立刻终止连接，丢失可能残留数据

## 简短面试版总结
1. TCP挥手是**操作系统内核TCP协议栈**执行，应用程序只是调用close触发。
2. 应用程序异常退出（panic、kill -9）：OS会回收fd。
   - recv缓冲区无剩余数据：内核发FIN，正常四次挥手；
   - recv缓冲区还有未读数据：内核发RST，直接重置连接。
3. 整机断电：内核无法发送任何报文，依靠TCP保活超时断开。

# TIME_WAIT：完全由**操作系统内核**维护，和应用程序无关
## 1. 什么时候进入 TIME_WAIT
四次挥手的完整收尾：
1. 我方收到对方 FIN，回复 ACK
2. **我方进入 TIME_WAIT 状态**（注意：是**主动关闭方**才会进入 TIME_WAIT，被动关闭方不会）

> 角色区分：
> - 主动close：先发FIN的那一端 → 最后发ACK，进入 `TIME_WAIT`
> - 被动close：收到FIN后回复ACK，自己再发FIN → 收到最后ACK直接进入CLOSED，**没有TIME_WAIT**

## 2. 核心：应用早就结束了，内核还在扛着这个连接
当应用调用 `close()` 之后，用户态程序就**不再持有这个socket**了。
就算程序已经退出、进程消失，**内核的TCP协议栈依然保留这条连接的状态，等待2MSL**。
- 2MSL：Maximum Segment Lifetime，报文在网络里最大存活时间。Linux默认一般是60s。

### 为什么必须等待2MSL（两个目的）
1. **保证最后那个ACK报文能送达对端**
   我方发给对方的最后ACK，如果丢包了：对方会重发FIN。
   如果我方已经直接关闭连接，收到重传FIN就只能回RST，对端认为连接异常。
   TIME_WAIT期间，内核还保留连接状态，收到对方重传FIN，会**重发ACK**。

2. **防止旧连接的延迟报文，被新复用的连接接收**
   网络里可能有滞留的迟到数据包。等2MSL之后，旧连接所有报文全部在网络消失，避免新建立的socket收到老连接的脏包。

## 3. 高频面试坑点
### ① TIME_WAIT 占用端口！
TIME_WAIT是内核维护的**连接四元组（源IP、源端口、目的IP、目的端口）**。
> 客户端大量短连接场景（每次请求新建socket），客户端端口会被TIME_WAIT占满，短时间内端口耗尽，无法新建连接。
> 服务端默认监听固定端口，服务端**一般不会产生大量TIME_WAIT**（因为服务端大多是被动关闭方）。

举例子：客户端访问HTTP服务，客户端主动关闭连接 → 客户端产生TIME_WAIT。

### ② 能不能跳过TIME_WAIT？
Linux提供 `SO_LINGER` 选项：
- 设置 `SO_LINGER` 超时为0，调用close时，**直接发送RST，跳过四次挥手，不会进入TIME_WAIT**
⚠️ 代价：粗暴断开，可能丢失缓冲区数据，不适合普通业务。

还有 `tcp_tw_reuse` / `tcp_tw_recycle` 内核参数：
- `tcp_tw_reuse`：允许在满足条件时，**复用处于TIME_WAIT的端口**（推荐）
- `tcp_tw_recycle`：老方案，NAT环境下极易出问题，新版Linux已经移除，不要用

## 4. 和刚才的话题联动：程序crash场景
如果程序异常崩溃，内核自动close：
- 如果本次是**主动关闭方**：内核发FIN，完成挥手后，内核依旧进入TIME_WAIT，和应用是否存活无关。
- 如果触发RST断开：不会进入TIME_WAIT，连接直接释放。

## 极简面试一句话总结
TIME_WAIT 是**内核TCP栈维护的状态**，应用进程早就退出了，内核依然保留连接等待2MSL；只有**主动关闭连接的一方**才会进入TIME_WAIT，目的是保障ACK送达、避免旧报文干扰新连接；它会占用源端口，短连接客户端容易出现大量TIME_WAIT。

## 顺带对比几个容易混淆状态归属
- FIN_WAIT_1 / FIN_WAIT_2 / TIME_WAIT / CLOSE_WAIT / LAST_ACK：**全部内核维护**
- 应用只负责：调用 close/shutdown 触发关闭，**不维护任何TCP状态机**

# CLOSE_WAIT
一句话：**CLOSE_WAIT 是【被动关闭方】的内核状态，堆积 CLOSE_WAIT 几乎都是应用代码的bug**

## 1. 怎么进入 CLOSE_WAIT（时序）
假设：客户端主动关闭连接，先发FIN给服务端
1. 客户端（主动方）发送 FIN → 进入 FIN_WAIT_1
2. 服务端内核收到这个 FIN，内核立刻回复 ACK
3. **此时服务端内核进入 CLOSE_WAIT**
> ✅ 内核已经知道对方关了，并且通知应用：对端不再发数据过来了。
> 内核在这个阶段**等待应用程序调用 close()**！

重点区分：
- TIME_WAIT：内核等报文（等2MSL，**不需要应用参与**）
- CLOSE_WAIT：内核**等应用代码**去关闭socket fd！内核啥也做不了，只能原地等。

## 2. 完整流程正常情况
服务端内核收到FIN → ACK，进入CLOSE_WAIT → **应用读到EOF（read返回0）** → 应用调用close(fd)
- 应用close后：内核发出FIN，进入LAST_ACK
- 收到对方最后ACK → 内核直接CLOSED，连接释放。

## 3. CLOSE_WAIT 堆积的根本原因
> **内核收到对端FIN，通知应用，但是应用迟迟不调用 close 关闭socket文件描述符。**
> fd一直被进程持有，内核就一直卡在 CLOSE_WAIT，不会发FIN，连接僵住。

### 常见代码场景（面试高频）
1. **goroutine / 线程阻塞在 read/recv 之外的逻辑，没有及时退出**
Go例子：
```go
// net.Conn.Read 返回 io.EOF（对方关闭），但是代码卡住没执行conn.Close()
buf := make([]byte,1024)
n,err := conn.Read(buf)
if err == io.EOF {
    // 读到EOF，代表对方发了FIN
    go heavyWork() // 启动协程处理，主流程忘记close
    // 没有 conn.Close()！！fd还在，CLOSE_WAIT
}
```
> 对方已经挥手结束，服务端读到EOF，但是代码没有关闭连接，fd不释放 → CLOSE_WAIT。

2. 错误的异常分支，**忘记close，fd泄漏**
很多代码只在正常路径close，异常分支漏掉close，socket fd泄漏。

3. 阻塞在写（write/send），没有处理连接关闭信号
对方发FIN，内核读缓冲区标记EOF，但应用一直在循环写数据，一直不read，永远感知不到EOF，永远不close。

> 核心：**CLOSE_WAIT 不是内核参数问题，99%是代码fd泄漏**。内核无能为力，只能等应用释放fd。

## 4. 怎么看和怎么清理
- 查看：`netstat -an | grep CLOSE_WAIT` / `ss -ti`
- 特点：**CLOSE_WAIT 是附着在进程上的！**
只要进程还活着，fd不关闭，这个CLOSE_WAIT就一直存在；
**杀掉这个进程，OS回收fd，CLOSE_WAIT瞬间消失**。
> 和TIME_WAIT不一样：TIME_WAIT不需要进程存活，内核独立持有。

## 5. 面试必背对比：CLOSE_WAIT vs TIME_WAIT
| 状态 | 属于哪一方 | 谁在等待 | 原因 | 能不能靠内核参数解决 |
|---|---|---|---|---|
| TIME_WAIT | 主动关闭方 | 内核，等待网络报文（2MSL） | 保证ACK送达，防止旧包干扰 | 可以调内核参数优化 |
| CLOSE_WAIT | 被动关闭方 | 内核等应用调用close() | 对方发FIN，应用不关闭fd | ❌ 内核参数无效，只能改代码 |

## 6. 一个经典坑
很多人遇到大量CLOSE_WAIT，去调Linux tcp内核参数，**完全没用**。
内核参数解决TIME_WAIT，**解决不了CLOSE_WAIT**。CLOSE_WAIT本质是应用层资源泄漏。

## 极简面试总结
CLOSE_WAIT是被动关闭方内核收到对端FIN、回复ACK之后的状态；内核等待应用调用close释放fd。大量CLOSE_WAIT堆积是**代码bug（socket fd泄漏）**，内核无法自动释放，杀掉进程才会消失，调内核参数无效。
