# Protobuf
业务层和传输层之间序列化和反序列化的网络通讯协议。
也可以用作数据格式存储到分布式缓存。

压缩比高，效率高；使用简单，提供兼容，易维护；可读性差，加密性好；跨平台，跨编程语言，且提供了不同语言的代码自动生成工具；
## 原理
编码后的二进制数据由一个个feild组成，每个feild由tag和value组成，如果field没有赋值，编码的时候不会被写入。tag包含了field-num（5位）、wire-type（3位）信息`Tag = (field_number << 3) | wire_type`。

protobuf使用**varint编码**编码整数，具有压缩效果，其编码高位有特殊含义：如果是1，表示后续的字节也是该数字的一部分；如果是0，表示这是最后一个字节，且剩余7位都用来表示数字（字节顺序由低到高处理，数值型是变长的，除非使用fixed整形型、浮点型或其他）。负数时，以ZigZag辅助编码。整数由tag和value组成。

string类型的value使用UTF编码，由tag-length-value组成。

**ProtoBuf消息升级原则**
在实际的开发中会存在这样一种应用场景，既消息格式因为某些需求的变化而不得不进行必要的升级，但是有些使用原有消息格式的应用程序暂时又不能被立刻升级，这便要求我们在升级消息格式时要遵守一定的规则，从而可以保证基于新老消息格式的新老程序同时运行。规则如下：
1. 不要修改已经存在字段的标签号。
2. 任何新添加的字段必须是optional和repeated限定符，否则无法保证新老程序在互相传递消息时的消息兼容性。
3. 在原有的消息中，不能移除已经存在的required字段，optional和repeated类型的字段可以被移除，但是他们之前使用的标签号必须被保留，不能被新的字段重用。
4. int32、uint32、int64、uint64和bool等类型之间是兼容的，sint32和sint64是兼容的，string和bytes是兼容的，fixed32和sfixed32，以及fixed64和sfixed64之间是兼容的，这意味着如果想修改原有字段的类型时，为了保证兼容性，只能将其修改为与其原有类型兼容的类型，否则将打破新老消息格式的兼容性。


## 对比
### protobuf与thrift
thrift嵌入thrift RPC服务框架，没有独立的序列化及反序列化接口，很难与其他协议灵活嵌套（如HTTP）。
protobuf提供了IDL和IDL编译器及编码和解析的API，对开发人员友好。压缩比高，编码解析速度也快。
protobuf非常适用于对性能要求高的RPC调用，还可以嵌入HTTP，利用HTTP的良好的跨防火墙的访问。也非常适用于压缩比高，编码解析速度要求快的持久化场景。

从test分支会有“proto协议比release分支先行”这个问题，gitlab/protocenter这种方式有同样的问题，除非我们用test/uat/release/feature 这套gitflow来维护proto协议发版。但是用这套gitflow，会导致proto协议更容易发生冲突（proto字段下标冲突），而且不同环境需要各维护一套proto版本，更容易出问题。所以，一般还是选择一个分支来打tag这种方式。至于如果对test分支有疑问，我们做个专用的proto分支也是一样的，feature分支里修改go.mod来选择不同的tag就行。关键的问题还是做到proto协议兼容，新增字段的下标单调增长且唯一，修改字段仅限于校验部分。

# protobuf 相对于原生数据、http协议的性能提升和编解码损耗
Protobuf 与 JSON/文本格式、原生二进制数据以及 HTTP 协议栈结合使用时，性能表现差异显著。以下从负载大小、序列化速度、编解码开销、协议栈整体收益四个维度系统分析。

## 一、相对于 JSON/文本格式：显著提升
1. 负载大小
- 数据类型	Protobuf vs JSON
+ 数字密集型（ID、时间戳、指标）	Protobuf 通常 4–5× 更小
+ 字符串密集型（名称、URL）	仅约 4% 更小（字符串本身存储方式相近）
+ 混合数据（典型 API 负载）	通常 50–85% 更小，整体为 JSON 的 20–50%

Protobuf 通过以下机制实现压缩：  
+ 字段标签替代字段名：JSON 重复传输 "field_name" 字符串，Protobuf 仅用 1 字节数字标签
+ Varint 变长整数编码：小整数只需 1–2 字节，JSON 每个数字字符占 1 字节
+ 无引号、无空白符、无花括号

2. 序列化/反序列化速度
- 操作	Protobuf vs JSON
+ 序列化（写入）	3–6× 更快，极端场景（纯数字数组）可达 85% 提升
+ 反序列化（读取）	5–10× 更快
+ 高吞吐量 CPU 占用	同请求量下 CPU 降低 30–50%

JSON 解析需要：文本分词 → 处理转义序列 → 字符串转数字。Protobuf 直接按偏移量读取二进制字段，无需文本解析。

##  二、相对于原生二进制（Raw Binary）：存在损耗
Protobuf 并非"零拷贝"格式，与手写原生二进制布局相比，存在明确的编解码开销：
1. 编解码损耗来源
- 损耗点	说明
+ Varint 逐字节解析	变长整数的 MSB（最高有效位）延续标志意味着解析器必须逐字节扫描才能确定字段边界，无法直接按固定偏移量跳转
+ 标签-值解析	每条字段需先解码字段编号（tag）和线类型（wire type），再决定如何读取后续字节
+ 内存分配	反序列化需在堆上分配目标对象图，深层嵌套消息可能触发数百次小内存分配
+ 数据拷贝	网络包缓冲区中的数据被拷贝到新分配的堆变量中

在高吞吐量微服务中，反序列化阶段可能消耗总处理时间的 40%。

2. 与 FlatBuffers / Cap'n Proto 的对比
- 特性	Protobuf	FlatBuffers / Cap'n Proto
+ 读取方式	解析 → 分配 → 拷贝	零拷贝，直接内存映射访问
+ 序列化速度	快	更快（数据已处于可序列化格式）
+ 随机字段访问	需完整解析	可直接跳转偏移量
+ 适用场景	通用 RPC、微服务	嵌入式、游戏引擎、高频交易

Protobuf 在"性能-可维护性-生态"三角中取了平衡，但不是绝对性能最优的原生二进制方案。

## 三、在 HTTP 协议栈中的影响（gRPC vs REST）
当 Protobuf 与 HTTP/2 结合（gRPC）对比 JSON + HTTP/1.1（REST）时，收益是协议层与序列化层的叠加：
- 指标	gRPC (Protobuf + HTTP/2)	REST (JSON + HTTP/1.1)	差距
+ 小负载延迟（1KB）	2.3 ms p50	10.1 ms p50	gRPC 快 77%
+ 负载大小	~50–200 字节	~500–2,000 字节	10× 更小
+ 单核吞吐量	50,000–100,000 RPS	15,000–35,000 RPS	2–3× 更高
+ 头部大小	~40 字节（HPACK）	~700 字节（未压缩）	~17× 更小
+ p99 尾延迟（高并发）	9 ms	34 ms	3.7× 更低
+ 单请求 CPU	~12 μs	~38 μs	3.2× 更低

收益来源：
+ HTTP/2 多路复用：单 TCP 连接承载数百并发 RPC，无队头阻塞
+ HPACK 头部压缩：重复头部字段只需传输索引
+ Protobuf 二进制编码：消除 JSON 的字段名、引号、空白符开销
+ 持久连接：避免 HTTP/1.1 频繁的 TCP/TLS 握手

注意：如果 REST 也使用 HTTP/2 + MessagePack/CBOR 等二进制格式，差距会缩小至 10–25%。

## 四、编解码损耗的量化与场景差异
Protobuf 的性能优势并非在所有场景下都成立：

小负载场景（< 1KB，简单对象）
- 对比	结果
+ Protobuf vs JSON	JSON 可能更快。Protobuf 的 schema 验证、代码生成对象创建开销在小数据量下可能抵消二进制优势
+ 典型场景	浏览器 API、配置读取、调试接口

中等负载（数字数组，1K–100K 元素）
- 对比	结果
+ Protobuf vs JSON	Protobuf 显著领先。Packed repeated 字段使数字序列极紧凑，序列化速度可快 75–85%
+ 典型场景	指标上报、日志批量传输、IoT 传感器数据

文本/嵌套密集型（大量字符串、Map、嵌套对象）
- 对比	结果
+ Protobuf vs JSON	尺寸仍占优，但速度优势减弱甚至逆转。字符串在两者中存储方式相近，Protobuf 的 length-delimited 解析和对象实例化带来额外 CPU 成本
+ 典型场景	用户资料、文档传输、富文本内容

纯原生二进制对比
- 对比	结果
+ Protobuf vs Raw Binary	原生二进制更快。手写 struct 直接内存映射，无 varint、无 tag 解析、无堆分配。但失去跨语言、schema 演进、版本兼容能力
+ 典型场景	游戏状态同步、内核网络栈、嵌入式固件

## 五、核心权衡总结
```plain
┌─────────────────────────────────────────────────────────────┐
│  需要人类可读 / 浏览器直接调试 / 快速原型  →  JSON            │
│  需要跨语言强类型 / schema 演进 / 中等吞吐量  →  Protobuf     │
│  需要极致性能 / 零拷贝 / 微秒级延迟  →  FlatBuffers/SBE     │
│  需要绝对控制 / 单语言 / 无依赖  →  手写原生二进制           │
└─────────────────────────────────────────────────────────────┘
```
Protobuf 的本质定位：它不是"最快"的序列化方案，而是在性能、可维护性、生态成熟度之间取得了最佳平衡。对于绝大多数微服务场景，其 3–10× 的序列化速度提升和 2–5× 的负载压缩，足以抵消编解码引入的 varint 解析和内存分配开销。
