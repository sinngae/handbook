# varchar(10) 比 varchar(100)更省运行时的内存空间吗？
这个说法在特定历史版本和特定场景下成立，但在现代 MySQL（8.0+）中已基本不成立，属于过时的优化观念。

## 一、核心结论
表格
场景	VARCHAR(10) vs VARCHAR(100)	说明
磁盘存储	完全一样	都只存实际内容 + 1~2 字节长度前缀
InnoDB 缓冲池（Buffer Pool）	完全一样	按实际行大小加载
内存临时表（MySQL 8.0+）	完全一样	TempTable 引擎按实际数据大小分配
内存临时表（MySQL 5.7 及更早）	VARCHAR(10) 可能更省	MEMORY 引擎临时表按声明最大长度分配
排序缓冲区（sort buffer）	基本一样	现代版本按实际内容长度处理

## 二、为什么会有这个传言？
MySQL 5.7 及更早版本的"黑历史"
在旧版本中，当查询需要创建内存临时表（如 GROUP BY、DISTINCT、UNION 等）时：
```sql
SELECT name, COUNT(*) FROM users GROUP BY name;
```
如果 name 是 VARCHAR(100)，内存临时表会为每一行预留 100 字节的空间；如果是 VARCHAR(10)，则只预留 10 字节。这在数据量大时确实会造成内存浪费。

但有两个重要前提：
+ 仅当查询被迫使用内存临时表时才会触发
+ MySQL 8.0 已改用 TempTable 引擎，完全按实际数据大小动态分配，此问题已消失

## 三、现代 MySQL（8.0+）的真实行为
```sql
-- 查看当前内存临时表引擎
SHOW VARIABLES LIKE 'internal_tmp_mem_storage_engine';
-- 默认值：TempTable（MySQL 8.0.16+）
```
TempTable 引擎的特性：
按实际存储内容动态分配内存
VARCHAR(100) 存 'hello' 只占用 5 + 1 = 6 字节
与声明的最大长度无关

## 四、唯一还可能存在差异的场景
即使到了 MySQL 8.0，以下极端场景仍有细微差别：
表格
场景	差异原因	实际影响
某些排序操作	排序缓冲区可能按最大长度做长度编码	极小，可忽略
连接缓冲区（Join Buffer）	嵌套循环连接时的行缓存	按实际行大小，无差异
存储过程变量/临时表字段	显式声明的内存表字段	若用 MEMORY 引擎，仍有差异

## 五、实践建议
不要为了"省内存"而故意设短
```sql
-- ❌ 错误做法：为了省内存把字段设得很短
VARCHAR(20)  -- 用户名，结果中文昵称被截断

-- ✅ 正确做法：给业务留足余量
VARCHAR(100) -- 用户名，安全且不影响性能
```
### 真正该关注的是什么？
表格
关注点	说明
索引长度限制	InnoDB 索引前缀上限 3072 字节，超长字段做索引需限制前缀长度
行大小限制	单行最大 65535 字节（不含 BLOB/TEXT），是硬上限
网络传输	返回大字段会增加带宽，但这是结果集问题，与 VARCHAR 声明长度无关
内存临时表切换磁盘	temptable_max_ram 默认 1GB，超了会转磁盘，这才是内存瓶颈

## 六、一句话总结
VARCHAR(10) 和 VARCHAR(100) 存同样的内容，运行时内存占用在现代 MySQL 中基本一致。 为了省内存而缩短 VARCHAR 是过时的微优化，代价是数据截断风险，收益几乎为零。该多长就多长。
