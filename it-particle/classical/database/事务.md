# 事务

## 事务的特性 ACID
+ 原子性 atomicity，要么完成，要么全部回滚
    + 客户端连接开启事务，要么提交、要么回滚
    + 客户端异常断开，mysql尽快检测到网络中断，检测到后立即回滚未提交的事务
        + 没有重连？业务处理失败返回，由上游重试
+ 一致性 consistency  
    + 实际并发的结果与理论串行结果一致  
    + 事务执行前后，处于一致状态？
+ 隔离性 isolation  
    + 同一时间仅有一个事务处理同一数据，处理这一数据的其他事务串行化处理，失败的事务不影响数据  
    + 多个事务并发执行，相互独立。
+ 持久性 durability  
    + 已提交的事务永久地更改数据保存在数据库中，不会回滚

ACID是传统数据库设计概念，追求强一致性，带有数学严谨性。
工程思维上更多使用支持BASE的大型分布式系统，牺牲强一致性，获取高可用性。比如，Elasticsearch、MongoDB、Redis Cluster等。

要素	全称	含义
BA	Basically Available	基本可用：系统出现故障时，允许损失部分可用性（如响应变慢、降级服务），但不完全瘫痪
S	Soft state	软状态：允许数据在一段时间内处于中间状态（不一致），不要求实时一致
E	Eventually consistent	最终一致性：不保证实时一致，但保证在没有新更新的情况下，数据最终会达到一致

## 隔离性的底层原理
实现的方式有两种，write ahead logging 和 shadow paging。
+ 后者简单开销大，一个事务修改的块都提交到磁盘，很难并发。
+ 前者对数据的修改必须记录到日志中，日志被冲刷到永久存储器中。不需要冲刷数据页。出现崩溃的时候，从日志恢复数据库。  


## 各种隔离的数据并发问题
+ 1.脏读，read-uncommited 的问题
在一个事务中读取了另一个事务未提交的数据

+ 2.不可重复读，read-commited的问题
一个事务中多次查询数据库，却因另一事务的(更新?)提交，造成查询结果不同

+ 3.幻读（查询了未提交插入的表数据）  
一个事务中多次统计或查询的结果集，因另一事务的(插入/删除?)提交，导致查询结果不同

## SQL标准中的四个隔离级别

隔离级别由低到高：
+ Read-uncommited  - 读未提交，无保证
+ Read-commited  - 读已提交，可避免1
+ Repeatable-read  - 可重复读，可避免1、2
+ serializable  - 串行化，可避免1、2、3发生

隔离级别即数据库处理并发的锁定策略，隔离级别越高，可并发程度越低。

> mysql默认repeatable-read，支持四种隔离级别；
> oracle只支持serializable和read-commited，默认为后者；
> DB2特有的的四种隔离级别（非标准）；
> 其他大多read-commited；

数据库可以设置默认的隔离级别，一个客户端的连接中也可以指定隔离级别，或者具体的sql语句指定锁行为。

```sql
-- mysql 查看事务隔离级别
select @@tx_isolation;

-- 设置
set [global|session] transaction isolation level '[isolate level name]';
set tx_isolation='[...]'
```
