# 接口设计是应该使用float32还是float64？还是采用放大倍数的形式？还是无损的字符串的形式？
这是一个经典的接口设计权衡问题，没有绝对答案，核心在于你的业务对精度的敏感度和系统的兼容性要求。以下是决策框架：

## 一、四种方案的适用场景
表格
方案	精度	传输体积	解析性能	跨语言兼容性	典型场景
float32	~7位有效数字	4字节	最快	好	3D坐标、传感器读数、颜色值、物理模拟
float64	~15-16位有效数字	8字节	快	好	科学计算、地理位置（经纬度）、普通统计值
放大倍数（定点数）	完全精确	4-8字节	快	最好	金额、汇率、税率、任何涉及钱的字段
字符串	完全无损	大	慢	最好	超大整数（如区块链交易ID）、精确小数、人类可读优先

## 二、关键决策原则
1. 涉及钱 → 绝对不要用浮点数
❌ {"price": 19.99}           // float64 无法精确表示 19.99
✅ {"price": 1999, "unit": "cent"}  // 放大100倍，用整数
✅ {"price": "19.99"}         // 字符串，由服务端/客户端精确解析
浮点数的二进制表示天生无法精确存储某些十进制小数（如 0.1），金额计算会累积误差。

2. 需要精确小数且范围不大 → 放大倍数
比如百分比存为整数（rate: 1250 表示 12.50%），重量存为毫克等。好处是：
零精度损失
跨语言无歧义（不会遇到 JavaScript 0.1 + 0.2 !== 0.3 的问题）
存储和计算都高效

3. 科学/工程测量值 → float64 通常足够
经纬度、温度、压力等连续物理量，float64 的 15 位精度远超传感器精度，且节省带宽（相比字符串）。

4. 超大数字或极高精度 → 字符串
比如区块链的 token 数量（可能超过 2^53）、高精度金融衍生品定价，字符串是唯一可靠选择。

## 三、一个实用的混合策略
{
  "amount": 199900,        // 金额：整数，单位"分"，精确无歧义
  "weight": 1250,          // 重量：整数，单位"克"或按协议定
  "latitude": 39.9042,     // 坐标：float64，精度足够
  "temperature": 23.5,     // 温度：float64，物理测量值
  "ratio": "0.3333333333", // 需要精确表示的比率：字符串
  "bigNumber": "999999999999999999999"  // 超大数：字符串
}

## 四、避坑提醒
坑	说明
+ JavaScript 的 Number 是 float64	如果接口消费者主要是 JS，整数超过 2^53 - 1（约 9007 万亿）必须用字符串，否则会丢失精度
+ JSON 标准不区分 float32/float64	大多数 JSON 库统一按 float64 解析，如果你用 float32 序列化，接收方可能拿到更精确的值（或反之）
+ 浮点数比较不要用 ==	接口校验时，0.1 + 0.2 == 0.3 会失败，这是语言无关的浮点特性

一句话总结：钱和精确比率用放大倍数或字符串，物理测量值用 float64，只有对带宽极度敏感且精度要求低的场景才考虑 float32。
