# 浮点数先存到DB，再取出，发生了变化，为什么？
浮点数入库再取出发生变化，通常不是数据库的"bug"，而是浮点数二进制表示的本质缺陷加上类型宽度不匹配导致的。以下是逐层拆解：

## 一、根本原因：浮点数无法精确表示很多十进制小数
计算机用二进制存储浮点数。就像十进制无法精确表示 1/3（只能写 0.3333...），二进制也无法精确表示很多十进制小数。

plain
十进制 0.1  →  二进制 0.0001100110011...（无限循环）
所以当你把 0.1 存入数据库，它已经被迫截断为一个近似值。取出时如果显示精度足够高，你会看到：

plain
0.10000000000000000555...
这不是数据库改了你的数据，而是它从来没被精确存储过。

## 二、最常见的几个具体场景

### 场景1：程序用 double（64位），数据库字段是 float（32位）
表格
环节	类型	精度
程序变量	double / float64	~15位有效数字
数据库字段	FLOAT / real	~7位有效数字
取回程序	double / float64	~15位有效数字（但数据已被截断）

流程：
plain
程序: 123456789.123456789 (double, 精确到15位)
  ↓ 存入
DB:   FLOAT 只保留 ~7位有效数字 → 123456790.0（或近似值）
  ↓ 取出
程序: 123456790.000000000 (double, 但精度已永久丢失)

解决方案：数据库字段改为 DOUBLE / double precision / FLOAT8，与程序类型宽度一致。

### 场景2：十进制字符串 ↔ 二进制浮点的往返转换
如果你通过 SQL 直接插入一个十进制字面量：
sql
INSERT INTO t VALUES (0.1);  -- 0.1 是十进制字符串
数据库解析器把它转成内部二进制浮点存储。再查询时：
sql
SELECT * FROM t;
客户端把二进制浮点转回十进制字符串显示。这个十进制→二进制→十进制的往返过程，可能让最后一位发生变化。

验证方法：
sql
-- 在 MySQL/PostgreSQL 中，用更高精度显示
SELECT CAST(my_float AS DECIMAL(30, 20)) FROM t;
-- 你会看到 0.10000000000000000000 后面跟着非零数字

### 场景3：ORM / 驱动层的类型转换
某些数据库驱动或 ORM 在映射时做了额外处理：
Java: ResultSet.getDouble() 从数据库二进制浮点构造 Java double，如果数据库是 DECIMAL 类型，驱动可能先转 BigDecimal 再转 double，引入额外舍入。
Python: float 是 C 双精度，但某些 ORM（如早期 SQLAlchemy）对 REAL 和 DOUBLE PRECISION 处理不一致。
JavaScript: 如果中间经过 JSON，0.1 可能被序列化为 0.10000000000000000555，接收方再解析时精度已经漂移。

### 场景4：数据库客户端的显示格式化
有时数据实际存储值没变，但客户端做了格式化：
Navicat/DBeaver 等工具默认只显示 6 位小数
printf("%.6f", value) 会自动四舍五入
命令行客户端可能有默认精度设置
验证方法：用十六进制查看内部表示，或转换为大精度 DECIMAL 查看。

## 三、如何定位你的具体问题
按这个顺序排查：
表格
步骤	操作	目的
1	查看表结构：DESCRIBE table 或 \d table	确认字段是 FLOAT 还是 DOUBLE
2	用高精度查询：SELECT CAST(col AS DECIMAL(30,20))	看实际存储的精确值
3	在程序里打印原始字节的十六进制表示	排除显示层干扰
4	检查 ORM/驱动的类型映射配置	确认没有自动类型转换

## 四、解决方案
表格
需求	推荐方案
金额、汇率、精确财务计算	用 DECIMAL(p,s) / NUMERIC，或存整数（分/厘）
科学计算、传感器数据	确保程序与数据库都用 DOUBLE / FLOAT8，接受微小误差
需要绝对精确且范围大	用字符串 VARCHAR 存储，程序端用精确数学库（如 Java BigDecimal、Python decimal）
已有系统出现精度问题	把 FLOAT 字段改为 DOUBLE 只能缓解，根治需换 DECIMAL

一句话总结：浮点数"变化"的本质是你看到的十进制数与计算机存储的二进制数本就不是同一个东西，数据库只是忠实存储了那个近似值。如果业务不能容忍这种近似，不要用浮点数存精确数据。
