# ES冷热分离时间配置（ILM索引生命周期）
> 核心：**用 ILM（Index Lifecycle Management），`min_age` 控制阶段迁移时间**
> ⚠️ 重点坑：**rollover滚动索引后，时间是从【滚动时间】开始算，不是索引创建时间**（数据流/别名滚动方案）；如果不用rollover（每日固定索引），min_age才是索引创建时间。
> 时间单位：`d`天、`h`小时、`m`分钟、`s`秒，例如 `7d`、`24h`

## 1. 业务示例需求
- Hot热阶段：写数据，主分片到50GB 或者写入满7天，触发rollover，新建索引，旧索引进入生命周期计时
- Warm温阶段：**滚动后7d** 迁移到warm节点，合并段、减少副本
- Cold冷阶段：**滚动后30d** 迁移到cold节点，降低优先级（8.x推荐searchable_snapshot可搜索快照）
- Delete删除：**滚动后90d** 删除索引

## 2. 创建ILM策略API（直接复制执行）
```json
PUT _ilm/policy/hot_warm_cold_policy
{
  "policy": {
    "phases": {
      "hot": {
        "actions": {
          "rollover": {
            "max_primary_shard_size": "50gb",
            "max_age": "7d"
          },
          "set_priority": {
            "priority": 50
          }
        }
      },
      "warm": {
        "min_age": "7d",    // ✅ 滚动7天后，进入温层
        "actions": {
          "allocate": {
            "require": {
              "data": "warm"
            }
          },
          "forcemerge": {
            "max_num_segments":1
          },
          "set_priority": {
            "priority":20
          }
        }
      },
      "cold": {
        "min_age": "30d",   // ✅ 滚动30天后，迁移冷节点
        "actions": {
          "allocate": {
            "require": {
              "data": "cold"
            }
          },
          "set_priority": {
            "priority":5
          }
        }
      },
      "delete": {
        "min_age": "90d",   // ✅ 滚动90天后删除索引
        "actions": {
          "delete": {}
        }
      }
    }
  }
}
```
> 7.x版本：`allocate` 用来绑定节点属性；**ES8推荐Data Tier（数据层），不再手动allocate，直接写`data_warm`/`data_cold`层**，节点打`data_hot/data_warm/data_cold`角色标签。

## 3. 绑定ILM策略到索引模板（数据流/别名）
```json
PUT _index_template/log_template
{
  "index_patterns": ["logs-*"],
  "template": {
    "settings": {
      "index.lifecycle.name": "hot_warm_cold_policy",
      "index.lifecycle.rollover_alias": "logs_write"
    }
  }
}
```
然后创建写入别名，初始化第一个索引：
```json
PUT logs-000001
{
  "aliases": {
    "logs_write": {
      "is_write_index": true
    }
  }
}
```

## 4. 两种时间模式区分（面试重点）
### ✅ 模式A：rollover滚动索引（推荐，日志/时序）
`min_age` = **索引rollover的时间**，不是索引创建时间
举例：索引2026-10-01创建，10-03满足条件rollover，那么warm的`min_age:7d`，是从10-03开始算，10-10进入温层。

### ✅ 模式B：不使用rollover，按索引创建时间（比如按天创建索引 `logs-2026.10.14`）
这种模板**不能写rollover**，min_age直接基于索引`@timestamp`/索引创建时间。
```json
"phases":{
    "warm":{"min_age":"7d"}, // 索引创建7天后进温
    "cold":{"min_age":"30d"}
}
```

## 5. Kibana图形界面配置（可视化设置冷热时间）
1. 堆栈管理 → Index Lifecycle Policies
2. 新建策略：
    - Hot阶段：开启Rollover，设置max_size/max_age
    - Warm：开启，`Move data into phase when` → 7 days
    - Cold：开启，`Move data into phase when` →30 days
    - Delete：开启，90 days
3. 保存策略，绑定Index Template

## 6. 重要注意事项&踩坑
1. ILM默认**每10分钟检查一次索引状态**，时间到了不会立刻迁移，最多延迟10分钟，参数：`indices.lifecycle.poll_interval`
2. min_age**必须递增**：warm 7d → cold必须 ≥7d，不能写warm30d cold15d，不生效
3. 节点标签：
    - 7.x：节点属性 `node.attr.data: hot/warm/cold`
    - 8.x Data Tier：节点角色 `data_hot,data_warm,data_cold`，不需要手动allocate，ILM自动调度
4. cold阶段8.x优先使用**可搜索快照searchable_snapshot**，不再是普通节点分片，节省大量磁盘
5. forcemerge是**只读操作**，进入warm阶段会把索引置只读，不能写入

## 7. 常用时间选型参考（日志场景）
- 热：最近7天（高频查询）
- 温：7~30天，查询变少
- 冷：30~90天，极少查询，归档
- 保留90天自动删除

# ES ILM 冷热索引完整迁移时序记录（rollover滚动索引场景，ES8 Data Tier）
> 前提：
> - 策略：hot→warm（rollover后7d）→cold（rollover后30d）→delete（rollover后90d）
> - ILM轮询：**默认10分钟检查一次索引状态**，不会时间一到立刻执行，存在最高10min延迟
> - 时间基准：**所有min_age从rollover滚动时刻开始计时，不是索引创建时间**
> - ES8 Data Tier：节点角色 `data_hot / data_warm / data_cold`，ILM自动执行`migrate`，不用手动allocate分配标签

## 整体流转时序（日志场景示例）
1. **阶段1：Hot热阶段（写入阶段）**
    - 创建索引 `logs-000001`，绑定写入别名`logs_write`，分片分配在hot节点
    - 持续写入数据；设置rollover条件：主分片50GB 或者索引存活7d，满足任一就触发rollover
    - ✅ 触发rollover动作：
      1. 将当前索引`logs-000001`的别名`is_write_index=false`，停止写入
      2. 新建索引`logs-000002`，`is_write_index=true`，新数据写入新索引
      3. **记录rollover时间点**（这个时间是后续所有min_age计算起点）
      4. 旧索引`logs-000001`仍然留在hot节点，进入等待倒计时

2. **等待：rollover后7天，到达warm阶段min_age阈值**
    ILM下一次轮询检测：索引已经满足`min_age:7d`，进入warm阶段，依次执行动作：
    1. `set_priority`：索引优先级降低（比如50→20），集群重启恢复时，热索引优先恢复
    2. `read-only`：索引置只读，禁止写入
    3. `forcemerge`：强制合并段，合并成1个segment，清理已删除文档（很重IO操作）
    4. `migrate`自动迁移分片：修改`_tier_preference=data_warm`
        - 分片开始从hot节点**重建迁移**（不是移动文件，ES分片是复制+删除旧分片）
        - 先在warm节点创建副本分片，数据同步完成，主分片切换，删除hot上旧分片
    5. 等待warm阶段**所有动作全部执行完毕**，开始等待cold阶段倒计时（继续基于rollover时间）
    > ⚠️重点：**必须当前phase全部action执行完成，才会进入下一阶段等待**；如果forcemerge或者分片迁移卡住，不会往下走。

3. **等待：rollover后30d，到达cold阶段min_age阈值**
    ILM轮询检测，进入cold阶段：
    1. `set_priority`：继续降低优先级（20→5）
    2. ES8推荐：`searchable_snapshot`（可搜索快照）
        - 把索引快照存入对象存储（S3/OSS），集群本地只保留少量元数据，大幅节省磁盘
        - 或者传统模式：migrate分片迁移到cold节点机械盘
    3. 索引冻结freeze，减少内存占用；
    4. 全部动作完成，继续倒计时，等待delete阶段

4. **等待：rollover后90d，到达delete阶段min_age阈值**
    ILM检测到时间满足，执行delete动作，**直接删除整个索引，释放磁盘**

# ✅ 分片迁移底层原理（重要）
ES**没有“移动分片文件”**，冷热迁移本质是：
1. 修改索引的`_tier_preference`（数据层偏好）
2. 集群分片分配器，在目标层节点（warm/cold）新建分片副本
3. 数据复制同步完成，分片主副角色切换
4. 源节点（hot/warm）上旧分片被删除
> 迁移过程中**索引可读**，但是会占用集群IO、网络；业务查询不受中断，但是大索引迁移会拉高负载。

# 🔍 查看迁移状态命令（记录排查）
```bash
# 查看索引当前ILM状态，当前阶段、阶段进入时间、执行动作、失败原因
GET logs-000001/_ilm/explain
```
返回关键字段：
- `phase`：当前阶段 hot/warm/cold
- `phase_entry_date`：进入本阶段的时间
- `action`：当前正在执行的动作（forcemerge/migrate等）
- `step`：当前步骤，`completed`代表动作执行完毕

```bash
# 查看分片分配情况，看分片在哪个节点
GET logs-000001/_cat/shards?v
# 查看节点角色
GET _cat/nodeattrs?v
```

# ⚠️ 迁移过程中常见阻塞场景
1. **forcemerge长时间卡住**：warm阶段强制合并大索引，IO打满，ILM停在forcemerge，不会继续迁移分片
2. 目标warm/cold节点资源不足、磁盘水位到达高水位，分片无法分配，migrate动作阻塞
3. 集群状态红色/黄色，分片无法分配，ILM动作暂停，直到集群恢复
4. min_age顺序写反（warm30d cold15d）：策略非法，无法流转

# 两种模式区分
1. **Rollover滚动索引（推荐时序日志）**
min_age = rollover时间；索引写完之后，等待N天迁移下一层。
2. **按天索引不使用rollover（logs-2026.10.14）**
min_age = **索引创建时间**；索引创建7天后直接进入warm，没有rollover步骤。
